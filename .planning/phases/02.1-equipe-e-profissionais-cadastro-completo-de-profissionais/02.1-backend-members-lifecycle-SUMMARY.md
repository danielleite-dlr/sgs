## Decisions Made

- **Invitation migration does not violate "sem migration".** The CONTEXT's no-migration decision is scoped to `Member`/deactivation ("o modelo Member já tem todas as colunas necessárias... Desativação usa as colunas existentes"). `member_invitations` is a different table with no equivalent columns, and the CONTEXT's own decisions section separately requires `InviteMemberInput` to carry `seniorityTier`/`isProfessional` — impossible without somewhere to store them between invite and accept. The fix is the smallest possible: two additive, nullable/defaulted columns, no backfill, no touch to any existing column, and `Member` itself appears nowhere in the `schema.prisma` diff for this phase (verified via `git diff` — see Self-Check).
- **Active commission rule informs, never blocks deactivation.** An orphaned commission rule doesn't leave a client unattended (unlike an appointment), stays fully readable through `CommissionsService.list()`, and structurally can't be reassigned to the now-inactive member because `commissions.service.ts:216-222` already requires `status: 'active'` on any `memberId` reference. Blocking on it would strand the admin without protecting anyone, so the payload simply reports `activeCommissionRuleCount` for the UI to display.
- **Exact payload signatures the frontend plan will consume:**
  - `allMembers: [Member!]!` — same `Member` shape as `members`, now including `status: MemberStatus!`.
  - `updateMember(input: UpdateMemberInput!): UpdateMemberPayload!` → `{ member: Member, errors: [UserError!]! }`. `UpdateMemberInput { id: UUID!, roleName: String, isProfessional: Boolean, seniorityTier: SeniorityTier }` — all fields but `id` optional; `seniorityTier: null` explicitly clears.
  - `deactivateMember(id: UUID!): DeactivateMemberPayload!` → `{ member: Member, futureAppointmentCount: Int!, blockingAppointments: [BlockingAppointment!]!, activeCommissionRuleCount: Int!, errors: [UserError!]! }`. `BlockingAppointment { id: UUID!, startsAt: DateTime!, clientName: String!, serviceName: String! }` (top 5, ascending by `startsAt`). On block: `member: null`, `errors: [{ code: 'MEMBER_HAS_FUTURE_APPOINTMENTS', message }]`.
  - `reactivateMember(id: UUID!): ReactivateMemberPayload!` → `{ member: Member, errors: [UserError!]! }`, no guard, idempotent.
  - Error codes used: `MEMBER_NOT_FOUND`, `ROLE_NOT_FOUND` (field `roleName`), `MEMBER_HAS_FUTURE_APPOINTMENTS`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] InvitationResolver.invite's organization lookup always failed under RLS**
- **Found during:** Task 3, while running the new `inviteMember` HTTP tests
- **Issue:** `this.prisma.organization.findUniqueOrThrow({ where: { id: tenantCtx.organizationId } })` ran on the raw, unscoped `PrismaService`. `organizations` has `FORCE ROW LEVEL SECURITY` keyed on the `app.current_organization` session variable, which is only ever set inside `TenantContextService.runWithTenant`. Outside that scope the policy always evaluates to false, so the lookup always threw `NotFoundError` — meaning `inviteMember` was broken for every caller, always, in this exact shape. It was never caught before because the only prior caller of this code path (`rbac.e2e-spec.ts`) is not discovered by Jest's `testRegex` (hyphen instead of dot).
- **Fix:** Wrapped the lookup in `this.tenant.runWithTenant(tenantCtx.organizationId, tx => tx.organization.findUniqueOrThrow(...))`.
- **Files modified:** `apps/backend/src/identity/invitation.resolver.ts`
- **Verification:** `members-lifecycle.e2e.spec.ts` → "inviteMember só com { email, roleName } continua funcionando" and the configured-invite test both pass.
- **Committed in:** `7048853` (Task 3 commit)

**2. [Rule 3 - Blocking] New e2e spec required FastifyAdapter + default supertest import to actually run**
- **Found during:** Task 3, first attempt to run `members-lifecycle.e2e.spec.ts`
- **Issue:** Copying the assembly pattern from `rbac.e2e-spec.ts` literally (`moduleRef.createNestApplication()` with no adapter, `import * as request from 'supertest'`) fails outright: the app boots on Fastify (`@nestjs/platform-express` isn't even installed), and `@types/supertest@6.0.3` vs `supertest@7.2.2` makes the namespace import uncallable under this project's exact dependency versions. Both failure modes are latent in all 4 hyphen-named integration spec files (`rbac.e2e-spec.ts`, `invitation.e2e-spec.ts`, `auth.e2e-spec.ts`, `full-auth-flow.e2e-spec.ts`) — they would hit the identical errors the day someone renames them to be Jest-discoverable, on top of the naming issue already tracked in STATE.md.
- **Fix:** In the new file only: `app = moduleRef.createNestApplication(new FastifyAdapter())`, `await app.getHttpAdapter().getInstance().ready()` before issuing requests, and `import request from 'supertest'` (default import) instead of the namespace import. Confirmed correct via `phase2-modules-boot.spec.ts`, which already uses this pattern successfully.
- **Files modified:** `apps/backend/test/integration/members-lifecycle.e2e.spec.ts`
- **Verification:** All 16 tests in the file pass.
- **Committed in:** `7048853` (Task 3 commit)
