# Phase 02.1: Equipe e profissionais — Research

**Researched:** 2026-09-28
**Domain:** CRUD interno sobre padrões já estabelecidos (NestJS/GraphQL schema-first + Prisma/RLS + React/Apollo/RHF+Zod). Nenhuma biblioteca nova, nenhuma pesquisa de ecossistema externo.
**Confidence:** HIGH — todos os achados vêm de leitura direta do código do repositório, não de treinamento/heurística.

## Summary

Esta fase não introduz stack nova: estende três arquivos backend (`members.service.ts`, `members.resolver.ts`, `identity.graphql`), cria mutations seguindo o padrão exato de `invitation.resolver.ts`/`commissions.service.ts`, e cria uma tela nova (`/profissionais`) seguindo o padrão exato de `ClientesPage`/`ClienteEditPage`. O achado mais importante da pesquisa é que **o precedente para `status` já existe e já é consumido**: `appointments.service.ts:104-109` e `commissions.service.ts:216-222` já filtram `status: 'active'` (junto com `deletedAt: null` e `isProfessional: true`) ao validar um `memberId` referenciado. Isso significa que passar a escrever `status: 'inactive'` em `deactivateMember` já bloqueia automaticamente, sem nenhuma mudança nesses dois arquivos, que um membro inativo seja escolhido em novo agendamento ou nova regra de comissão — a guarda já existe no código de Fase 2/3.

O segundo achado crítico: `MembersService.listActive()` filtra **apenas** `deletedAt: null` (nunca `status`). Hoje isso é inofensivo porque nenhum membro tem `status !== 'active'` (a coluna nunca é escrita fora do `status: 'active'` no create). No momento em que `deactivateMember` passar a escrever `status: 'inactive'`, a query `members` (consumida por `MemberCombobox`/`CommissionRuleForm` no Fase 2 e pela agenda) começará a **listar profissionais inativos no picker de agendamento/comissão** — um bug de regressão silencioso — a menos que o filtro seja atualizado. Ao mesmo tempo, a tela `/profissionais` precisa listar TODOS os membros (ativos e inativos, com badge de status) para permitir reativação — não pode reusar cegamente a mesma query sem parâmetro.

**Primary recommendation:** usar **apenas `status`** (não `deletedAt`) para `deactivateMember`/`reactivateMember`. `deletedAt` no model `Member` nunca é escrito hoje em lugar nenhum do código — é reservado para uma futura remoção definitiva que não faz parte desta fase. Ajustar `MembersService.listActive()` para também filtrar `status: 'active'` (mantém contrato idêntico para os consumidores atuais, já que hoje 100% dos membros têm status active) e adicionar um novo método (ex.: `listAll(orgId)`, sem filtro de status) exposto por uma nova query GraphQL (ex.: `allMembers`) para a tela `/profissionais`.

## Architecture Patterns

### Padrão de mutation com payload de erro (`identity.graphql` / `invitation.resolver.ts`)

```typescript
// Source: apps/backend/src/identity/invitation.resolver.ts:22-56
@RequirePermission(PERMISSIONS.MEMBER_INVITE)
@Mutation('inviteMember')
async invite(
  @Args('input') input: { email: string; roleName: string },
  @CurrentUser() user: JwtAccessPayload,
  @CurrentTenant() tenantCtx: TenantContext,
) {
  try {
    const result = await this.invitations.invite({ ...tenantCtx, ...input });
    return { invitationId: result.invitationId, expiresAt: result.expiresAt, errors: [] };
  } catch (e) {
    if (e instanceof AuthError) {
      return { invitationId: null, expiresAt: null, errors: [{ code: e.code, message: e.message }] };
    }
    throw e;
  }
}
```

Duas variantes de "erros como dado" coexistem no repo:
1. **try/catch de exceção de domínio** (`AuthError`) — usado em `invitation.resolver.ts`. Exceções lançadas pelo service viram `errors: [{code, message}]`.
2. **`errPayload()` helper retornado direto pelo service** (sem exceção) — usado em `commissions.service.ts:16-19` e `clients.service.ts:12-16`. `UserError` tem `code`, `message`, `field?: string | null`.

**Para `updateMember`/`deactivateMember`/`reactivateMember`, seguir o padrão 2** (helper `errPayload` no `MembersService`, resolver fino sem try/catch) — é o padrão dominante em toda a Fase 2 (`commissions.service.ts`, `clients.service.ts`, `categories.service.ts`), e `MembersService` hoje não lança exceções de domínio.

### Onde os DTOs de input ficam
`apps/backend/src/catalog/commissions/dto/commission.input.ts` — classes com `class-validator` (`@IsEnum`, `@IsOptional`, `@IsUUID`, `@Matches`). Criar `apps/backend/src/identity/dto/member.input.ts` (não existe hoje — `identity/` não tem pasta `dto/`; `invitation.resolver.ts` usa tipos inline `{ email: string; roleName: string }`, mas o padrão de Fase 2 estabelecido é DTO com class-validator). Recomendo criar o DTO explícito para `UpdateMemberInput` dado que `seniorityTier` deve ser validado contra o enum.

### SDL — onde estender
`apps/backend/src/graphql/schema/identity.graphql`:
- `Member` type (linhas 14-22) já expõe todos os campos necessários para leitura — **não precisa mudar**, exceto se a tela precisar do campo `status` (hoje **não exposto** — `listActive()` não seleciona `status`). **Adicionar `status: String!` ao tipo `Member`** é necessário para a tela mostrar o badge de status.
- `InviteMemberInput` (linhas 26-29) — adicionar `seniorityTier: SeniorityTier` e `isProfessional: Boolean` (opcionais, com default no service).
- Novas mutations: `updateMember(input: UpdateMemberInput!): UpdateMemberPayload!`, `deactivateMember(id: UUID!): DeactivateMemberPayload!`, `reactivateMember(id: UUID!): ReactivateMemberPayload!`.
- Nova query (recomendada): `allMembers: [Member!]!` — ou adicionar parâmetro `members(includeInactive: Boolean): [Member!]!`. Ver seção "Runtime State Inventory" abaixo — **este é o ponto de maior risco de regressão da fase.**
- `SeniorityTier` enum já existe em `catalog.graphql:94-98` (`junior`, `pleno`, `senior`) e é compartilhado via cross-SDL reference (mesmo padrão que `Member` já usa, comentado em `identity.graphql:24`: *"SeniorityTier enum is defined in catalog.graphql"*).

### `@RequirePermission` + `@CurrentTenant` — mecânica
```typescript
// Source: apps/backend/src/identity/members.resolver.ts:16-20
@RequirePermission(PERMISSIONS.MEMBER_READ)
@Query('members')
async listMembers(@CurrentTenant() tenantCtx: TenantContext) {
  return this.members.listActive(tenantCtx.organizationId);
}
```
`@CurrentTenant()` injeta `{ organizationId, memberId }` extraído do JWT/header já validado pelo guard de tenant. Todo acesso a dados passa por `TenantContextService.runWithTenant(orgId, tx => ...)`, que faz `SET LOCAL app.current_organization` dentro de uma transação — é isso que ativa a RLS do Postgres. **Nunca acessar `PrismaService` direto para dados de tenant** — sempre via `this.tenant.runWithTenant`.

### Anti-Patterns to Avoid
- **Não copiar o padrão "toast undo" de `ClientesPage.handleDelete`** para desativação de membro. Em Clients, restore só é acessível nos 5s do toast porque a query `clients()` filtra `deletedAt: null` e clientes deletados somem da lista — não há botão de restore na UI para um cliente já fora da tela. Membros **precisam continuar visíveis** (com status "inativo") para permitir reativação a qualquer momento — é um requisito explícito do CONTEXT.md ("Desativar / reativar" como ações persistentes na lista, coluna "status" visível). Usar uma query que devolve todos os membros + badge de status + ação "Reativar" direta no dropdown, sem depender de toast.
- **Não reimplementar o aceite de convite.** `InvitationPage` (`apps/frontend/src/features/auth/pages/InvitationPage.tsx`) já existe e é pública, ligada em `/convite/:token`. Reusar sem alteração.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Payload de erro de mutation | Novo shape de erro | `UserError { code, message, field }` já definido em `identity.graphql` (reaproveitado de `catalog.graphql`/`clients.graphql`) | Consistência de contrato — frontend já sabe renderizar esse shape |
| Bloqueio de escopo/status por regra de negócio | `enum` novo `MemberStatus` no GraphQL | `status: String!` (VarChar 20, valores `"active"`/`"inactive"` por convenção, sem enum no schema Prisma) | Column já existe sem enum Postgres — criar enum GraphQL sobre uma coluna string livre é decisão de discretion, mas não requer migration; ver nota abaixo |
| Isolamento de tenant | Middleware Prisma custom | `TenantContextService.runWithTenant` | Já implementado e testado desde Fase 1; é o único caminho que ativa RLS |
| Formulário de edição (papel/senioridade) | Componente de form do zero | Padrão `AdjustStockDialog.tsx` (Dialog + RHF + Zod + `useMutation` com `cache.evict`) | Fase 2 já estabeleceu esse padrão para edições rápidas de 2-3 campos |
| Confirmação de ação destrutiva (desativar) | Novo modal de confirmação | `ConfirmSoftDeleteDialog` — adicionar `'member'` a `SoftDeleteEntityKind` | Componente genérico já parametrizado por `entityKind`, com i18n chaveado |

**Nota sobre enum de status:** `status` no Prisma é `String @default("active") @db.VarChar(20)` — **não é um enum de banco**. Não criar um enum GraphQL rígido (`enum MemberStatus { active inactive }`) é aceitável, mas se criado, é só no SDL (sem migration), similar ao já feito com `SeniorityTier`. Ambas as abordagens (String simples vs enum GraphQL) são válidas; recomendo enum GraphQL para consistência com `SeniorityTier` e para o frontend não lidar com string mágica.

## Common Pitfalls

### Pitfall 1: Atualizar `listActive()` sem quebrar a tela `/profissionais`
**O que dá errado:** se `listActive()` passar a filtrar `status: 'active'` (necessário para não vazar inativos nos pickers), a MESMA função não pode ser reusada pela tela `/profissionais`, que precisa listar TODOS os membros (para mostrar e reativar os inativos).
**Como evitar:** criar um segundo método no service (`listAll(orgId)`, sem filtro de status) e uma segunda query GraphQL (`allMembers` ou `members(includeInactive: Boolean = false)`). Não sobrecarregar a query `members` existente com um comportamento diferente por padrão — isso quebraria silenciosamente os testes de `commission-rule-form.test.tsx` que fazem mock de `MembersQuery` sem esperar um novo argumento obrigatório.
**Warning sign:** se o teste `commission-rule-form.test.tsx` (mock de `MembersQuery` sem variables) começar a falhar, é sinal de que a query mudou de shape incompatível com o consumidor existente.

### Pitfall 2: Desativar membro com agendamentos futuros ou regra de comissão ativa
**O que dá errado:** hoje NÃO existe nenhuma checagem que impeça desativar (ou remover `isProfessional`) um membro que já tem `appointments` futuros ou `commissionRules` vinculadas. As guardas em `appointments.service.ts`/`commissions.service.ts` só rodam na CRIAÇÃO de um novo agendamento/regra — não há trigger nem checagem no momento de desativar o membro.
**Consequência concreta se não tratado:** um agendamento futuro continua apontando para um profissional agora "inativo" (FK não impede, `Appointment.professional Member @relation` sem `onDelete` restritivo visível — soft-delete não aciona FK do Postgres). A agenda provavelmente ainda renderiza esse agendamento (não passa pelo filtro de `listActive`), mas o profissional não aparecerá mais no picker para NOVOS agendamentos. Uma `commissionRule` com `scopeType: member_service` para um membro inativo fica "órfã" — continua sendo lida por `commissions.service.ts:list()` (que não filtra por status do membro), mas nunca mais pode ser criada de novo para esse membro.
**Recomendação para o planner (discretion do CONTEXT.md):** a opção mais barata e consistente com o padrão de `categories.service.softDelete` (que bloqueia com `CATEGORY_HAS_CHILDREN`/`CATEGORY_HAS_SERVICES`) é **avisar, não bloquear** — retornar a contagem de agendamentos futuros/regras ativas como parte do payload ou como um `UserError` de aviso (não bloqueante) e deixar o admin confirmar. Bloquear duro (como `categories`) é mais seguro mas pode impedir o "pronto quando" do M1 se o admin testar desativação de um profissional com agenda cheia. Como o requisito de negócio é explicitamente "sem perder histórico" (preservar `appointments`/`commissionRules` passadas), a recomendação mínima seguinda seria: permitir desativar sempre, mas no frontend mostrar um `AlertDialog` (reusar `ConfirmSoftDeleteDialog`) com a contagem de agendamentos futuros, sem bloquear no backend.

### Pitfall 3: Esquecer de registrar a rota em `router.tsx`
**O que dá errado:** `/profissionais` só existe em `GATED_PATHS` e `menu-config.ts` — não em `PROTECTED_ROUTES`. Ligar `equipe: true` sem adicionar a entrada em `PROTECTED_ROUTES` faz `isPathEnabled('/profissionais')` retornar `true`, mas a rota não é filtrada para dentro de `enabledRoutes` porque **nunca esteve na lista de origem** — o app cai em 404 mesmo com a flag ligada.
**Como evitar:** adicionar a linha em `PROTECTED_ROUTES` no mesmo commit.

### Pitfall 4: `InviteMemberInput.seniorityTier`/`isProfessional` sem defaults
**O que dá errado:** se os campos novos forem obrigatórios no SDL, quebra qualquer client existente de `inviteMember` (não há outros hoje, mas quebra o teste `rbac.e2e-spec.ts` que chama `inviteMember` só com `{ email, roleName }`).
**Como evitar:** tornar `seniorityTier: SeniorityTier` e `isProfessional: Boolean` opcionais no SDL, com default (`isProfessional: false`, `seniorityTier: null`) no `InvitationService.invite()`.

### Pitfall 5: `status` como string livre sem normalização
**O que dá errado:** `status` é `VarChar(20)` sem CHECK constraint visível no schema.prisma (não confirmado — não há `@@check`). Se `deactivateMember` escrever `"inactive"` e algum outro código escrever `"disabled"` ou `"suspended"` no futuro, os filtros `status: 'active'` espalhados (`appointments.service.ts`, `commissions.service.ts`, `listActive()`) continuam funcionando (tudo que não é `'active'` já é tratado como "não elegível"), mas a tela precisa de um valor canônico único para renderizar o badge de "inativo".
**Como evitar:** fixar a constante `'active' | 'inactive'` como enum GraphQL (`MemberStatus`) e usar essa mesma literal em `deactivateMember`/`reactivateMember`.

## Open Questions

1. **Bloquear ou apenas avisar ao desativar membro com agendamentos futuros/comissões ativas?**
   - O que sabemos: nenhuma guarda existe hoje; o dado não se perde de qualquer forma (soft flag, não soft-delete de FK).
   - O que é incerto: se o produto quer impedir totalmente ou só avisar.
   - Recomendação: avisar no frontend com contagem, não bloquear no backend (ver Pitfall 2). Deixar o planner decidir a UX exata.

2. **`members` query ganha parâmetro opcional ou nova query dedicada (`allMembers`)?**
   - O que sabemos: qualquer mudança de shape na query `members` sem parâmetro tem que preservar 100% o comportamento atual (testado por `commission-rule-form.test.tsx`).
   - O que é incerto: preferência de nomenclatura do time (não há precedente de "query com filtro opcional booleano" no código atual — `clients()` usa parâmetros de paginação, não um toggle de estado).
   - Recomendação: nova query `allMembers` é mais segura (zero risco de regressão) do que adicionar parâmetro à query existente.
