# Quick Task 261105-c26: contrato começa pela noiva e cria o grupo - Context

**Gathered:** 2026-11-05
**Status:** Ready for planning

<domain>
## Task Boundary

Inverter o fluxo do contrato de noiva/debutante para seguir o dia a dia do Studio JS.

Hoje: cria-se o grupo (bridal_group) → adiciona a noiva → cria o contrato a partir do grupo (`createContract(input: { groupId, ... })`).
Na prática: a noiva faz contato → escolhe o pacote → o studio faz o contrato → a noiva assina → só depois vêm as acompanhantes.

Novo fluxo: Contratos › Novo contrato → escolher tipo (noiva/debutante), a cliente (noiva; ou debutante + responsável/contratante), data do evento, pacote, itens/serviços e pagamento. O grupo é criado automaticamente na mesma transação, só com a noiva/debutante como membro coberto pelo contrato. Depois de criado, o grupo aparece (link a partir do detalhe do contrato) para adicionar acompanhantes.

</domain>

<decisions>
## Implementation Decisions

### Acompanhantes
- Ficam FORA do contrato. Entram no grupo depois da assinatura, com serviços/pagamentos à parte, sem alterar o contrato aceito (snapshot/aceite intactos).
- Membros adicionados ao grupo depois de o contrato existir NÃO são "coberto pelo contrato" por padrão (não entram nos itens nem no PDF).

### Entrada
- Botão em Contratos › Novo contrato (não na ficha da cliente).
- O formulário de novo contrato não exige grupo pré-existente; cria o grupo por trás.

### Compatibilidade
- Manter o fluxo antigo (createContract com groupId de grupo existente) funcionando — há dados no staging/produção criados assim e testes que cobrem.
- Preferir não mexer no schema (Contract.bridalGroupId continua obrigatório; o grupo é criado automaticamente). Migration só se for realmente necessária.

### Claude's Discretion
- Forma da API: novo campo opcional no CreateContractInput (ex.: `newGroup: { eventKind, eventDate, brideClientId, responsibleClientId, name? ... }` mutuamente exclusivo com `groupId`) ou mutation nova — escolher o que reaproveitar melhor o código de BridalService (criação de grupo + membro) e ContractsService.create.
- Itens do contrato no novo fluxo referenciam o membro noiva criado na transação (ContractItemInput hoje exige groupMemberId) — resolver no backend (ex.: itens sem groupMemberId = noiva).
- Nome do grupo gerado automaticamente (ex.: "Noiva <nome>" / "Debutante <nome>") se o form não pedir.

</decisions>

- RLS forçada por `app.current_organization`; usar `this.tenant.runWithTenant(orgId, tx => ...)`.
