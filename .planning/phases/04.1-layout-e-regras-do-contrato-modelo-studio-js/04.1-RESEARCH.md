## Summary

**PDF: ficar no pdfkit 0.20.2.** Foi feito um protótipo (descartável, fora do repo) com o papel timbrado real: PNG RGBA 795x1122 com `doc.opacity(0.8)` + `doc.image(...)` em todas as páginas via evento `pageAdded`, margens 40/20/30 mm, `Helvetica` com acentos e `text(..., {align:'justify'})`. O PDF saiu com `/ca 0.8` (opacidade), canal alpha preservado (SMask), WinAnsi presente e quebra de página correta. Helvetica padrão do pdfkit usa codificação WinAnsi: cobre á é ç ã õ ê, travessão "—", aspas curvas e "º/ª". O que o pdfkit NÃO dá pronto são tabelas com colspan/altura variável, `**negrito**` inline e linhas de assinatura lado a lado; isso exige um helper pequeno (~200 linhas) em cima de `doc.heightOfString`, `doc.rect`, `doc.text` com `continued`/`width`. HTML→PDF (Puppeteer/Chromium) daria fidelidade automática de CSS, mas acrescenta ~400 MB de Chromium + fontes na imagem Alpine do backend, memória por request e CI mais lento (o job E2E já baixa Chromium só para Playwright); não vale para um layout fixo de 2 páginas.

**Armadilha encontrada que muda o desenho:** `doc.image(Buffer)` re-embute a imagem a cada página (o cache `_imageRegistry` só vale para `src` string). Usar `const img = doc.openImage(buf)` UMA vez e passar o objeto `img` em `doc.image(img, ...)` (o pdfkit usa `src.width && src.height` e embute o `image.obj` uma única vez). Sem isso um contrato de 4 páginas carrega a imagem 4 vezes.

**Armazenamento do papel timbrado: tabela imutável endereçada por hash no Postgres (bytea).** O backend em staging NÃO tem volume (`docker-compose.staging.yml` só tem volumes de postgres/valkey/meilisearch; o filesystem do container backend é efêmero) e R2 não existe no projeto. bytea + RLS é a única opção sem infra nova. Upload via mutation GraphQL com base64 (mesmo padrão já usado em `contractPdf`, que devolve base64); o REST não serve porque o `JwtAuthGuard` é GraphQL-bound. Exige subir o `bodyLimit` do Fastify (padrão 1 MiB) para ~4 MiB no `createFastifyAdapter`; o nginx do staging já permite 25m.

**Versionamento:** adicionar `contract_versions.snapshot JSONB NULL` + `format_version`. Versão nova = snapshot estruturado canônico; `text_sha256` passa a ser o SHA-256 do JSON canônico (chaves ordenadas) do snapshot, que inclui os textos das cláusulas já com variáveis aplicadas e o `letterheadSha256`. Versões antigas têm `snapshot = NULL` e seguem no PDF legado (a coluna `rendered_text` continua obrigatória; nas versões novas guarda uma renderização em texto puro do snapshot para o fallback e para busca). O fluxo de aceite (`textSha256` conferido em `accept`) não muda.

**Regra "itens do pacote" (D-05) — ponto crítico que o CONTEXT assume funcionar e NÃO funciona hoje:** `ContractItem.packageId` só é preenchido no caminho "pacote" de `buildItems` (create sem `items`). `ContractFormDialog.submit` ao EDITAR sempre envia `items: explicitItems`, e o caminho de itens explícitos grava `packageId: null` (ver `contracts.service.ts` linha ~147 e `update` chamando `buildItems(tx, group, input.items, null)`). Ou seja, depois de qualquer edição todos os itens viram "adicionais". É preciso preservar o vínculo (ver Pitfall 1 e a recomendação).

**Primary recommendation:** pdfkit + helper de tabela, snapshot JSON canônico em `contract_versions`, papel timbrado em `contract_letterheads` (bytea, imutável, por hash) apontado por `contract_settings`, parcelas do sinal em `contract_deposit_installments` com alocação pura por vencimento em `contract-math.ts`, itens do pacote preservados via flag no `ContractItemInput`, uma migration SQL (schema + RLS + seed Studio JS guardado por nome) e um script TS idempotente para gerar as novas versões dos contratos draft/awaiting.

### Pattern 1: Fundo em todas as páginas, embutido uma vez
**What:** abrir a imagem uma vez e desenhá-la a cada página nova, antes do conteúdo.
**When to use:** sempre que a org tiver papel timbrado.
**Example:** (protótipo executado; resultado `/ca 0.8`, 1 imagem de fundo com SMask)
```typescript
// Source: protótipo local com pdfkit 0.20.2 + trecho de pdfkit.js (image(): "if (src.width && src.height) image = src")
const mm = (v: number) => (v * 72) / 25.4;
const doc = new PDFDocument({
  size: 'A4',
  margins: { top: mm(40), bottom: mm(30), left: mm(20), right: mm(20) },
  bufferPages: true,
});
const bg = letterheadBuffer ? doc.openImage(letterheadBuffer) : null; // UMA vez
const paintBg = () => {
  if (!bg) return;
  doc.save();
  doc.opacity(0.8);
  doc.image(bg, 0, 0, { width: doc.page.width, height: doc.page.height });
  doc.restore();
};
paintBg();                       // página 1
doc.on('pageAdded', paintBg);    // demais páginas; o cursor volta para a margem superior depois do evento
```
Atenção: o evento `pageAdded` é disparado quando o pdfkit adiciona a página, antes do texto continuar, então o fundo fica atrás do conteúdo. O rodapé "Contrato CT-... página X de Y" existente (y = `page.height - 36`) cai DENTRO da faixa do rodapé dourado do papel (conteúdo termina em ~284 mm; rodapé começa aí): mover o rodapé do SGS para dentro da área útil (ex.: logo acima da margem inferior, y = 297 mm − 30 mm + 2 mm, fonte 7 pt) ou omiti-lo quando houver papel timbrado e colocar código/hash no bloco de aceite.

### Pattern 2: Helper de tabela (colspan, altura variável, quebra de página)
**What:** função `drawTable(doc, {x, width, columns:[pct...], rows:[{cells:[{text|runs, colspan, align, fontSize}]}]})`.
**Algoritmo:**
1. Para cada linha, converter colspans em larguras (`cols` em %, soma = largura útil 170 mm = 595,28 − 2·56,69 pt = 481,9 pt).
2. Altura da célula = `doc.heightOfString(texto, {width: w − 2·pad})` (pad = 5 px = 3,75 pt) + 2·pad; altura da linha = max das células. Linhas com sub-linha 7 pt (descrição do pacote): célula com duas runs (9,5 pt bold + 7 pt), somar as duas alturas.
3. Se `y + alturaLinha > doc.page.height − doc.page.margins.bottom`, chamar `doc.addPage()` (o `pageAdded` repinta o fundo) e continuar em `doc.page.margins.top`. Não repetir cabeçalho (as tabelas do modelo cabem na página 1; o teste de paginação garante que nenhuma linha é cortada).
4. Desenhar bordas com `doc.lineWidth(0.75).rect(x, y, w, h).stroke()` por célula (1 px CSS = 0,75 pt) e o texto com `doc.text(t, x+pad, y+pad, {width: w−2pad, lineBreak:true})`.
5. Desligar o auto-flow: sempre passar x/y explícitos e, ao final, setar `doc.x = left; doc.y = yFinal`.
**Cuidado:** `doc.text()` com y explícito perto do fim da página dispara `addPage` automático se ultrapassar `margins.bottom` — por isso a quebra deve ser decidida ANTES de desenhar a célula.

### Pattern 3: Texto rico `**negrito**` justificado
Converter cada parágrafo em runs `[{text, bold}]` (split por `/\*\*(.+?)\*\*/`). O pdfkit alterna fontes com `doc.font(bold?'Helvetica-Bold':'Helvetica').text(run, {continued:true, align:'justify'})` — `continued:true` mantém o fluxo e o `align:'justify'` funciona com `continued` desde que a última run feche com `continued:false`. Escapar `**` não pareados (tratar como texto literal). `lineGap` para entrelinha 1,3: `lineGap = 9.5 × 0.3 ≈ 2.85` pt (o pdfkit usa `lineGap` somado à altura natural da fonte; calibrar com o PDF de referência).
Assinaturas lado a lado: dois blocos de 40% de largura com `doc.moveTo().lineTo().stroke()` e texto centralizado abaixo, em y fixo (checar espaço restante; se não couber, `addPage`).

### Pattern 4: Snapshot canônico e hash
```typescript
// domain/contract-snapshot.ts (esboço)
export const SNAPSHOT_FORMAT = 2; // 1 = legado (sem snapshot)
export interface ContractSnapshot {
  format: 2;
  kind: 'noiva' | 'debutante';
  generatedOn: string;                 // YYYY-MM-DD (data local do studio)
  studio: { name; cnpj; address; representative; representativeRg; city; uf };
  letterhead: { sha256: string | null; mime?: string };
  title: string; intro: string; parties: string; trialNote: string;       // textos JÁ com variáveis aplicadas
  clauses: string;                     // II..VIII + disposições finais, variáveis aplicadas
  contractor: { name; cpf; rg; address; postalCode; email; phone1; phone2; phone3 };
  debutante: { name } | null;
  event: { date: string; time: string | null; locationName; serviceAddress };
  budget: {
    package: { name; description; priceCents } | null;
    extras: { label: string /* "Serviço Adicional: X – Pessoa" */; trial: boolean; cents: number }[];
    discount: { label: string; cents: number } | null;
    totalCents: number;
  };
  payment: {
    mode: 'sinal' | 'sinal_parcelado' | 'a_vista';
    installments: { seq: number; dueDate: string; cents: number }[];
    balanceDueDaysBefore: number | null; // null em a_vista
  };
}
// canonicalJson: JSON.stringify com chaves ordenadas recursivamente, sem espaços; sha256Hex(canonicalJson(snapshot))
```
O hash de aceite vira o hash do snapshot. `renderedText` = renderização em texto puro (para o `view` legado/telemetria e para o teste de regressão).

### Anti-Patterns to Avoid
- **Passar `Buffer` a `doc.image` a cada página** (embute N vezes). Usar `openImage` uma vez.
- **Renderizar o PDF aceito a partir do estado atual** do contrato/org: o PDF de uma versão aceita DEVE vir só do snapshot (+ papel timbrado por hash). Hoje isso já é verdade para o texto; manter.
- **Gravar a situação da parcela** (paga/vencida): derivar sempre (D-14).
- **Reutilizar `contract_settings.letterhead_bytes` mutável** para PDFs antigos: trocar o arquivo mudaria PDFs já aceitos. Usar tabela imutável por hash.
- **Incluir RG/CEP em `recordAudit.metadata`** ou em logs.

## Don't Hand-Roll

| Problema | Não construir | Usar | Por quê |
|----------|---------------|------|---------|
| Hash do documento | Concatenação ad hoc de campos | `canonicalJson` (ordenação recursiva de chaves) + `sha256Hex` existente | Estabilidade do hash entre execuções/Node; um único ponto de verdade |
| Tolerância de soma de parcelas | `Number` com float | Centavos inteiros (`toCents`/`fromCents` de `common/money`) | Evita erro de arredondamento; tolerância 1 centavo vira `Math.abs(diff) <= 1` |
| Mascaras de CPF/telefone | Novas máscaras | `formatCpf`/`validateCpf` em `features/clients/utils/cpf` e a máscara BR de telefone (fast-260929d); acrescentar só RG e CEP | Já testadas |
| Parsing do PNG/JPEG | Decodificar bytes | `doc.openImage(buf)` dentro de try/catch no upload | O pdfkit é o consumidor final; se ele abre, o PDF sai |
| Alocação do sinal | Estado gravado por parcela | Função pura `allocateInstallments` sobre `Σ ledger` | Ledger já é append-only com estorno (04 D-13); estorno desfaz alocação automaticamente |
| Código de erro/GraphQL | Novo mecanismo | `ContractError` + `mapContractError` (erros como dados em `errors[]`) | Padrão do módulo |
| Data por extenso | Tabela de meses | `Intl.DateTimeFormat('pt-BR',{day:'2-digit',month:'long',year:'numeric',timeZone})` | Gera "04 de novembro de 2026" (conferir o "de" no resultado; tem teste) |

**Key insight:** o difícil nesta fase não é o PDF em si, é manter UMA fonte da verdade (snapshot) usada pelo PDF, pela página pública e pelo hash. Qualquer renderização que leia o estado vivo em vez do snapshot quebra a garantia de D-18.

## Respostas às perguntas-chave

### 1. Motor de PDF — recomendação: pdfkit

### 5. Alocação por vencimento e alertas
**Onde:** `domain/contract-math.ts` (função pura, ao lado de `computeContractStatus`).
```typescript
export interface InstallmentInput { id: string; seq: number; dueDate: string; cents: number }
export type InstallmentState = 'paid' | 'partial' | 'open' | 'overdue';
export function allocateInstallments(
  installments: InstallmentInput[],
  netPaidCents: number,        // max(0, Σ ledger com estornos/devoluções) — mesmo cálculo de computeContractStatus
  today: string,
): { id: string; paidCents: number; pendingCents: number; state: InstallmentState }[] {
  let left = Math.max(0, netPaidCents);
  return [...installments]
    .sort((a, b) => a.dueDate.localeCompare(b.dueDate) || a.seq - b.seq)
    .map((i) => {
      const paid = Math.min(left, i.cents); left -= paid;
      const pending = i.cents - paid;
      const state = pending === 0 ? 'paid' : paid > 0 ? 'partial'
        : i.dueDate < today ? 'overdue' : 'open';
      // parcial e vencida: state 'partial' mas flag overdue = pending>0 && dueDate < today
      return { id: i.id, paidCents: paid, pendingCents: pending, state };
    });
}
```
Decisão: expor `overdue: boolean` separado do `state` (uma parcela parcialmente paga também pode estar vencida) — D-14 lista "paga / parcial / em aberto / vencida"; o enum de exibição pode ser derivado (`overdue` vence `partial` na UI, com o valor pago visível). O restante = `total − paid` após o sinal quitado, já calculado por `computeContractStatus` (`balanceCents`).
`validateInstallments(installments, depositCents)`: mínimo 1, valores > 0, datas válidas, Σ = depósito (±1 centavo), `a_vista` => exatamente 1 parcela com valor = total (sem restante). ## Common Pitfalls

### Pitfall 1: Itens do pacote viram "adicionais" depois da primeira edição
**What goes wrong:** orçamento do PDF perde a linha "Pacote contratado" e lista cada serviço como adicional.
**Why:** `buildItems(..., null)` no `update` e o caminho de itens explícitos gravam `packageId: null`; o front sempre envia `items` ao editar.
**How to avoid:** `packageItem` no `ContractItemInput` e propagação no front (seção 6). Teste de integração: criar por pacote, editar só o desconto, renderizar snapshot e conferir que `budget.package.priceCents` = preço do pacote e `extras` vazio.
**Warning signs:** `budget.package == null` com `contract.packageId != null`.

### Pitfall 2: Papel timbrado trocado altera PDFs já aceitos
**What goes wrong:** o PDF baixado depois do aceite tem outro fundo que o aceito.
**How to avoid:** tabela por hash imutável + `snapshot.letterhead.sha256`; nunca ler "o papel atual" no PDF de versão aceita.

### Pitfall 3: Imagem embutida N vezes / PDF gigante
**What goes wrong:** `doc.image(buffer)` por página.
**How to avoid:** `doc.openImage` uma vez (Pattern 1); teste que conta `/Subtype /Image` no PDF (bytes) e espera ≤ 2 (imagem + SMask) mesmo com 3 páginas.

### Pitfall 4: Conteúdo invade cabeçalho/filete/rodapé na quebra de página
**What goes wrong:** `doc.text` automático quebra usando as margens corretas, mas texto com `y` explícito (tabelas/assinaturas) não.
**How to avoid:** decidir a quebra antes de desenhar (Pattern 2), margens do documento fixas, testes que extraem a posição Y máxima (hook no helper: registrar `maxY` por página e asserir `≤ page.height − bottomMargin`). Rodapé do SGS dentro da área útil.

### Pitfall 5: `bufferPages` + `switchToPage` para rodapé e o evento `pageAdded`
O laço atual de rodapé (`switchToPage`) não repinta o fundo (já pintado) mas muda `doc.page.margins.bottom` para 0 temporariamente — manter o padrão e restaurar. Se o rodapé for escrito perto do limite com `margins.bottom` zerado, não gerar página extra (`lineBreak:false`, como hoje).

### Pitfall 6: Limite de body 1 MiB do Fastify
Upload base64 de > ~700 KB falha com 413 antes do GraphQL. Elevar `bodyLimit` (seção 2) e testar com imagem de 2 MB.

### Pitfall 7: Contratante ≠ noiva (debutante)
`bride_client_id` é usado como contratante em vários pontos: `accept()` (CPF_MISMATCH), `recordCashMovement.clientId`, `renderContractVersionTx` (nome/CPF), alertas (`brideName`), listagens. Introduzir `contractor_client_id` e passar por um helper; testar CPF do aceite com a responsável.

### Pitfall 8: Alertas retroativos
Backfill de 1 parcela por contrato existente gera alertas "vencida" no primeiro job. Mitigar: vencimento do backfill = data do aceite/criação e comunicar; ou criar parcelas só para contratos `draft/awaiting` e deixar `active` na regra antiga (preferível se o usuário não quiser ruído: decisão do planejador, default recomendado = contratos `active` com entrada já paga ganham parcela já "paga" por alocação, então não alertam; os não pagos alertam, o que é o comportamento desejado).

### Pitfall 9: Hash e normalização
Datas/valores no snapshot em formato canônico (strings ISO e centavos inteiros), sem `Date`/`Decimal` serializados por locale; ordenar arrays por chave estável (`seq`, ordem do orçamento). Teste: duas serializações do mesmo estado dão o mesmo hash; alterar qualquer campo visível muda o hash.

### Pitfall 10: Texto fora do WinAnsi
Emoji/caracteres fora do conjunto em nome, endereço ou textos editados somem ou geram caractere inválido. Sanitizar na entrada do PDF (e avisar em validação das Configurações).

export function canonicalJson(v: unknown): string {
  const norm = (x: unknown): unknown =>
    Array.isArray(x) ? x.map(norm)
    : x && typeof x === 'object'
      ? Object.fromEntries(Object.entries(x as Record<string, unknown>)
          .filter(([, val]) => val !== undefined)
          .sort(([a], [b]) => (a < b ? -1 : 1))
          .map(([k, val]) => [k, norm(val)]))
      : x;
  return JSON.stringify(norm(v));
}

export function parseBold(s: string): { text: string; bold: boolean }[] {
  const out: { text: string; bold: boolean }[] = [];
  s.split(/(\*\*[^*]+\*\*)/g).forEach((part) => {
    if (!part) return;
    const m = /^\*\*([^*]+)\*\*$/.exec(part);
    out.push(m ? { text: m[1], bold: true } : { text: part, bold: false });
  });
  return out;
}
